# BME Bot — دستیار تلگرامی دانشجویان مهندسی پزشکی

بات آموزشی برای دانشجویان BME: دانشنامه‌ی تجهیزات پزشکی (+ بخش تعمیرات و
نگهداری)، سنسورها/قطعات، پرسش‌های رایج، پرسش‌وپاسخ با AI، و چند ابزار
کمکی (OCR، تبدیل ویس به متن، کوییزساز + کوییز تصادفی از آرشیو، ویس-به-جزوه).
خوشامدگویی خودکار اعضای جدید گروه (قابل‌تنظیم از پنل ادمین)، و چند فیچر
(OCR) مستقیماً داخل گروه هم با Ephemeral Messages در دسترسه — بدون شلوغ‌کردن
گروه برای بقیه. پنل ادمین کامل (broadcast، جستجوی کاربر، آمار سلامت +
خطاهای اخیر، محدودیت‌های قابل‌تنظیم، تنظیمات بات).

## راه‌اندازی

```bash
pip install -r requirements.txt
apt install ffmpeg          # برای دو تایر fallback تبدیل ویس به متن
cp .env.example .env        # و مقداردهی
# users.db و medical_device.db باید در ریشه‌ی پروژه باشند
PYTHONPATH=src python -m bme_bot.app
```

## ساختار و قراردادهای مهم

- **دو دیتابیس کاملاً جدا، عمداً:** `users.db` (کاربر/مصرف/ادمین، از طریق
  `db/app_connection.py`) و `medical_device.db` (دانشنامه‌ی تجهیزات + جدول‌های
  `device_maintenance_*`، از طریق `db/equipment_connection.py`). هیچ‌وقت قاطی
  نشوند.
- **ترتیب ثبت handler در `app.py` حیاتی است:** همه‌ی `ConversationHandler`ها
  (admin ×۴، equipment_admin_edit، maintenance_admin_edit، welcome) باید *قبل* از
  `CallbackQueryHandler(callback_handler)` عمومی ثبت بشن — وگرنه دیسپچر عمومی
  زودتر و نادرست callback رو می‌قاپه و ConversationHandler هیچ‌وقت اجرا
  نمی‌شه. `tests/test_handler_registration.py` این ترتیب رو با یک
  `Application` واقعی (نه mock) تضمین می‌کنه؛ هر ConversationHandler جدید باید
  همون‌جا هم اضافه بشه.
- **namespace جدای callback_data برای هر ConversationHandler**
  (`admin_edit_field:`, `maint_admin_*:`, ...) — چون تشخیص کلیک روی
  دستگاه/اکشن با split محدود انجام می‌شه، یک prefix متفاوت لازمه تا با فرمت
  عمومی `device:action:line` قاطی نشه.
- **هر فیچر AI-محور: فایل/جدول مستقل خودش** (handler + `db/*_usage_repository.py`
  + `data/*_prompt.json` مستقل، نه مشترک) مگر ورودی/خروجیش عملاً همون فیچر
  باشه (مثل کوییز-از-فایل که `quiz_usage` رو با کوییز-از-متن مشترک گذاشت).
- **`services/ai_service.ask()` نقطه‌ی ورود مشترک همه‌ی فیچرهای AI** (ai_assistant،
  quiz، jozve). زنجیره: Gemini (`gemini/gemini-3.6-flash`) → Groq
  (`openai/gpt-oss-120b` → `qwen/qwen3.6-27b`) → OpenRouter. **سقف توکن روزانه‌ی
  Groq (۲۰۰,۰۰۰ توکن/روز) بین همه‌ی این فیچرها مشترکه** — محدودیت‌های سخت‌گیرانه‌ی
  jozve (۱/روز) و سقف ۴۰۹۶ کاراکتری کوییز-از-فایل هردو برای همین طراحی شدن.
- **محدودیت مصرف:** `db/feature_limits_repository.py` + `db/usage_limit_helper.py`
  (منطق SQL مشترک، allow-list صریح روی نام جدول چون پارامتر جای‌گذاری‌شده
  برای نام جدول وجود نداره). سقف/کول‌داون هر فیچر از پنل ادمین («🎚
  محدودیت‌ها») قابل‌تغییره، seed اولیه در `app_connection.py`. **ادمین در سطح
  handler معاف می‌شه**، نه در repository (اصلاً `check_*_limit` صدا زده
  نمی‌شه).
- **گزارش خطا سه لایه‌ست:** `utils/error_reporting.py`
  (`report_error`/`report_service_issue`، throttle ۱۰دقیقه‌ای، برای
  شکست‌های شناخته‌شده‌ی هر فیچر) + `utils/telegram_error_handler.py` (شبکه‌ی
  ایمنی سطح root logger، هر `logger.error` ناگرفته خودکار به
  `MAIN_ADMIN_CHAT_ID` می‌ره) + **لاگ فشرده‌ی خطای غیرمنتظره**
  (`utils/error_fingerprint.py` + `db/error_log_repository.py`): هر
  exception یه اثرانگشت «نوع@محل» می‌گیره (فقط عمیق‌ترین فریمِ کد خودمون،
  نه کتابخونه‌ها)؛ یک ردیف به‌ازای هر باگِ *یکتا*، نه هر رخداد — تکرار
  فقط `count`/`last_seen` رو به‌روز می‌کنه، نه traceback رو دوباره (نه
  توی جدول، نه توی فایل لاگ، نه توی alert تلگرام). نمای فشرده‌ش («🪲
  خطاهای اخیر») زیر «🩺 سلامت سیستم» در پنل ادمینه. لاگ فایل: truncate در
  ۵MB (نه rotate) — چون تکرار دیگه فایل رو پر نمی‌کنه، این سقف برای
  محتوای یکتا کافیه.
- **ذخیره‌ی عکس/ویدیوی تلگرامی:** برای محتوای تکراری/متغیر (مثل آیتم‌های
  تعمیرات) `file_id` تلگرام ذخیره می‌شه، نه بایت خام — طبق API تلگرام
  فایل ارسال‌شده با `file_id` بدون محدودیت و بدون آپلود مجدد قابل ارسال
  دوباره‌ست. (ستون `photo` قدیمی جدول `information` بایت خام داره — میراث
  import اولیه‌ی ۷۲ دستگاه، الگوی جدید نیست.)
- **قابلیت‌های Bot API جدیدتر از نسخه‌ی pin‌شده‌ی PTB (`==21.4`):**
  `bot.do_api_request(endpoint, data)` — راه رسمی خودِ PTB برای متدهای
  HTTP کاملاً جدید — و `api_kwargs={...}` روی متدها/کلاس‌های typed موجود
  (`bot.send_message`, `InlineKeyboardButton`, `MessageEntity`) برای
  فیلدهای جدیدتر روی چیزهای قدیمی (تأیید‌شده مستقیم با
  `inspect.signature`، نه فقط مستندات). شش utility مستقل، هرکدوم
  مستندسازی کامل خودش رو داره: `utils/button_style.py` (رنگ دکمه، Bot
  API 9.4)، `utils/date_time_entity.py` (entity نوع date_time، فیلد wire
  واقعیش `unix_time`ه نه `date_time`، دقت UTF-16 حیاتیه)،
  `utils/rich_message.py` (`sendRichMessage`، Bot API 10.1 — جدول بومی؛
  خروجی نهاییِ `/ask`/`/ai` و پیام جزوه‌ی jozve هردو از این استفاده
  می‌کنن، با fallback کامل به MarkdownV2 قدیمی)، `utils/draft_stream.py`
  (`sendRichMessageDraft`، Bot API 10.1+ — پیش‌نمایش تدریجیِ فرمت‌دار پاسخ
  `/ask` قبل از پیام نهایی، فقط چت خصوصی)، `utils/ephemeral.py`
  (`receiver_user_id` روی `send_message`، Bot API 10.2 — پاسخ داخل گروه
  که فقط فرستنده می‌بینه؛ فعلاً فقط OCR گروهی از این استفاده می‌کنه). هر
  شش‌تا کاملاً افزوده‌ن: روی هر خطا (حتی exception غیرمنتظره) بی‌سروصدا
  `False`/پیام معمولی برمی‌گردن و فراخواننده به مسیر قدیمی برمی‌گرده —
  آپگرید کل PTB عمداً انجام نشد (ریسک رگرشن رو کل پروژه، نامتناسب با این
  بهبودهای UI).
- **`bot_settings` (key→value عمومی، `db/settings_repository.py`):**
  تنظیمات سبکِ قابل‌تغییر از پنل ادمین بدون دیپلوی مجدد — اولین و فعلاً
  تنها مصرف‌کننده: فعال/غیرفعال + متن خوشامدگویی اعضای جدید گروه
  (`handlers/welcome.py`، زیر «⚙️ تنظیمات بات»). عمداً عمومی نگه داشته
  شده برای تنظیمات مشابه بعدی. **نکته‌ی امنیتی:** اسم تلگرام کاربر تازه‌عضوشده
  (که کاملاً دست خودِ اونه) قبل از جایگزینی در این قالب escape می‌شه
  (`welcome._escape_untrusted_name`) — بدونش، یه اسم مثل
  `[کلیک کنید](evil.com)` می‌تونست یه لینک قلابی داخل پیام رسمی بات بسازه.
  هر متن قالب جدیدی که ورودی کاربر توش substitute می‌شه باید همین الگو رو
  رعایت کنه.
- **`utils/typing_indicator.py` (`send_typing`):** نشانگر «در حال
  تایپ است...» قبل از هر پردازش کند (AI/OCR/STT/jozve/quiz) — فقط یه بار
  فرستاده می‌شه (نه با تمدید دوره‌ای)، چون مکملِ پیام‌های متنیِ «⏳ در حال
  پردازش» است، نه جایگزینشون.

- **بکاپ خودکار هفتگی `users.db` (`utils/db_backup.py`):** هر هفته
  (پیش‌فرض جمعه ۰۳:۰۰ تهران، job در `app._post_init`) یه snapshot سازگار با
  SQLite backup API گرفته می‌شه (نه کپی خام فایل — `users.db` در حالت WAL
  هست و بخشی از داده ممکنه فقط تو `-wal` باشه)، integrity_check می‌شه،
  gzip می‌شه و به *چت خصوصی همه‌ی ادمین‌ها* (نه گروه — شامل شناسه‌ی کاربرانه)
  فرستاده می‌شه؛ `BACKUP_KEEP` (پیش‌فرض ۴) نسخه‌ی آخر هم تو `backups/` می‌مونه.
  فقط `users.db` بکاپ می‌شه (`medical_device.db` عمداً نه). فایل بالای ۴۹MB
  فقط محلی می‌مونه و به ادمین‌ها هشدار می‌ره. تنظیمات: `BACKUP_ENABLED`،
  `BACKUP_DIR`، `BACKUP_KEEP`، `BACKUP_WEEKDAY` (0=یکشنبه…۵=جمعه، مطابق PTB)،
  `BACKUP_HOUR`. **بازگردانی دستیه:** بات رو خاموش کن، فایل رو gunzip کن،
  جای `users.db` بذار و `users.db-wal`/`users.db-shm` قدیمی رو پاک کن.
- **WAL و timeout (`db/_connection_factory.py`):** `users.db` با
  `journal_mode=WAL` و timeout ۱۰ثانیه‌ای اجرا می‌شه (`medical_device.db` عمداً نه).
  کنار `users.db` فایل‌های `-wal`/`-shm` هم ساخته می‌شن؛ کپی دستی فقط `.db`
  وقتی بات روشنه کامل نیست.
- **timeout و مسیرها:** `AI_REQUEST_TIMEOUT_SECONDS` (۶۰) و
  `AI_HEALTH_CHECK_TIMEOUT_SECONDS` (۱۵)؛ مسیر پیش‌فرض دیتابیس‌ها و آرشیو
  کوییز مطلقه (کنار ریشه‌ی پروژه).

- **قرارداد `medical_device.db` و ابزار بررسی (`tools/check_equipment_db.py`):**
  قبل از جایگزینی دیتابیس روی سرور اجرا کنید:
  `PYTHONPATH=src python tools/check_equipment_db.py path/to/medical_device.db`
  (فقط می‌خونه). قرارداد از کد: ردیف هر دستگاه `name == شناسه در device_line`؛
  «معرفی» = *کپشن عکس* با Markdown **قدیمی** (بولد تک‌ستاره `*x*`، سقف ۱۰۲۴
  واحد UTF-16، عکس الزامی)، بقیه‌ی بخش‌ها = Rich Markdown (بولد دو‌ستاره،
  جدول، سقف ۳۲۷۶۸ بایت؛ و اگر Rich رد شد، Markdown قدیمی با سقف ۴۰۹۶).
  `--fix out.db` یک *کپی* می‌سازد و فقط `**→*` در `definition` و تبدیل عکس‌های
  WebP به JPEG (نیاز به `pip install pillow`) را انجام می‌دهد. **هشدار
  استقرار:** این فایل جداول `device_maintenance_*` را ندارد؛ اگر روی سرور
  محتوای نگهداری ثبت شده، فایل را *جایگزین نکنید* — فقط ردیف‌های
  `information` را داخل دیتابیس زنده ببرید.

## تست

```bash
export PYTHONPATH=src && pytest tests/ -q
pyflakes src/ tests/ && pip check
```

فعلاً: ۷۳۸ تست پاس، pyflakes/pip check تمیز. **نکته‌ی مهم:** چند
فایل تست preexisting (jozve/ocr/stt/quiz/ai_assistant_rate_limit/app_routing)
موقع اجرا مستقیم رو `users.db` واقعی می‌نویسن، نه یه دیتابیس موقت — بعد از هر
اجرای کامل سوییت، `users.db`/`medical_device.db` رو با نسخه‌ی pristine چک/ریست
کن قبل از تحویل.

## نکات باز

- **ویرایش‌های ادمین روی `medical_device.db` (تجهیزات/نگهداری) بکاپ
  خودکار ندارن** (تصمیم صریح: فقط `users.db`) — خودتون گهگاهی کپی بگیرید.
- **قابلیت دیده‌نشده‌ی فاز بعد:** دکمه‌ی پنل ادمین برای دیدن ۱۰۰/۲۰۰/۳۰۰ خط
  آخر لاگ (عمداً بعد از بهینه‌سازی بیشتر سیستم لاگ).
- دو ردیف تکراری تو جدول `information`: `audiogram` (بی‌خطر) و `surgical_laser`
  (نسخه‌ی فعلاً نمایش‌داده‌شده `definition` خالی داره؛ نسخه‌ی کامل زیر یه `id`
  دیگه‌ست) — تصمیم حذف کدوم با شماست.
- `utils/persian_text.looks_like_persian()` عمداً به `ocr_service` وصل نشده
  (فیلتر زبانی، عکس انگلیسی رو هم رد می‌کرد؛ مشکل واقعی هالوسینیشن مدل
  ربطی به زبان نداشت) — تابع/تست‌هاش دست‌نخورده مونده برای استفاده‌ی آینده.
- تایر STT رسمی Google Cloud هنوز با یه ویس واقعی تلگرام تست نشده.
- کوییز از فایل: فقط docx/txt (نه pdf، نه .doc قدیمی) — طبق تصمیم صریح.
- **پیش‌نمایش تدریجی `/ask` (`utils/draft_stream.py`, `sendRichMessageDraft`)
  با یه بات/چت واقعی تست نشده** — امکانش تو این محیط نبود. طبق مستندات
  رسمی از اول مارس ۲۰۲۶ برای همه‌ی بات‌ها فعاله، ولی یه گزارش (نه رسمی از
  تلگرام) هست که این پیش‌نمایش‌ها تو چت خصوصی روی تلگرام iOS به‌شکل
  «Pinned Message» نمایش داده می‌شن (این گزارش اصلش برای نسخه‌ی
  plain-text قدیمی این قابلیت بود؛ برای نسخه‌ی rich-markdown فعلی جداگانه
  تأیید/رد نشده) — اگه بعد از استقرار این رو دیدید،
  `AI_STREAMING_ENABLED=false` رو در محیط ست کنید (بدون نیاز به تغییر
  کد)؛ خطاهای واقعی API خودشون خودکار fallback می‌کنن، این فلگ فقط برای
  همین یه حالت خاصه که هیچ exception ای تولید نمی‌کنه. نکته‌ی جداگانه‌ی
  این نسخه: هر گام یه prefix ناقص از rich markdown می‌فرسته که سینتکسش
  ممکنه (مثلاً وسط یه جدول در حال شکل‌گیری) نامعتبر باشه — عمداً پیچیده‌تر
  نشده، چون هر شکست وسط‌راه فقط همون پیش‌نمایش رو لغو می‌کنه، پیام نهایی
  همیشه مستقل و کامل می‌ره.
- **Ephemeral Messages برای OCR گروهی (`utils/ephemeral.py`,
  `handlers/ocr.handle_group_ocr_request`) با یه گروه واقعی تست نشده** —
  قابلیتیه که فقط از جولای ۲۰۲۶ (Bot API 10.2) وجود داره. روی هر خطای
  واقعی API، به یه پیام معمولی و قابل‌دیدن برای کل گروه fallback می‌کنه
  (رجوع به `ephemeral.send_or_fallback`) — یعنی بدترین حالت این نیست که
  جواب گم بشه، بلکه اینه که به‌جای فقط-برای-فرستنده، برای کل گروه دیده
  بشه.
- **خوشامدگویی با `filters.StatusUpdate.NEW_CHAT_MEMBERS`، نه
  `ChatMemberHandler`** (`handlers/welcome.py`) — چون `run_polling()`
  فعلی هیچ `allowed_updates` صریحی نمی‌ده و بدون اون، آپدیت‌های نوع
  `chat_member` اصلاً از تلگرام دریافت نمی‌شن. این مسیر ساده‌تر اکثر
  گروه‌ها رو پوشش می‌ده ولی یه سناریوی نادر (گروه‌هایی که «نمایش پیام
  عضویت» رو صریح خاموش کرده باشن) رو نه — ارتقا به `ChatMemberHandler`
  یه تغییر مجزا و مشخصه (نیازمند تغییر `run_polling` هم)، نه یه رگرشن.
- **برنامه‌ریزی‌شده، هنوز ساخته نشده:** دکمه‌ای در پنل ادمین برای دیدن
  ۱۰۰/۲۰۰/۳۰۰ خط آخر لاگ بات از داخل خودِ بات. عمداً به تعویق افتاده تا
  مشخص بشه سیستم فعلی لاگ (فرمت فشرده + dedup اثرانگشتی در `error_log`)
  برای این مصرف تازه کافیه یا نیاز به بازطراحی بیشتر داره.
